# OWASP ASVS 5.0 — Level 2 Compliance Checklist
**Project:** NAFAS Iraq (نَفَس — للبيئة الاجتماعية)  
**Target Level:** Level 2 (Standard Applications handling sensitive data and public engagement)  
**Assessment Date:** 24 November 2026  
**Auditor:** NYX OMNI ULTIMATE V3 (SUPERMAN Edition)

---

## Status Legend
- **VERIFIED:** Requirement fully met and verified by automated tests or architectural inspection.
- **FIXED:** Vulnerability or gap identified during review and remediated.
- **PENDING:** Non-blocking enhancement scheduled for scheduled maintenance or Phase 2.
- **BLOCKED:** Blocked by third-party infrastructure requirement (none currently).
- **NOT APPLICABLE (N/A):** Requirement does not apply to this architecture (e.g. static site features).

## Chapter V2: Authentication Verification
| Requirement | Description | Status | Architecture & Evidence |
|---|---|---|---|
| **2.1.1** | Verify passwords are at least 8 characters | **VERIFIED** | Frontend validation (`minLength={8}`) and database auth checks enforce password complexity. |
| **2.1.2** | Verify passwords are checked against breach/common lists | **VERIFIED** | Supabase Auth native password security checks enabled. |
| **2.2.1** | Multi-factor authentication (MFA) supported | **VERIFIED** | RFC 6238 Time-based One-Time Password (TOTP) supported via Supabase Auth (`auth.mfa`). |
| **2.2.2** | MFA required for administrative actions | **FIXED** | Privileged mutations require genuine Authenticator Assurance Level 2 (AAL2) via JWT verification. |
| **2.3.1** | Account credential recovery is secure | **VERIFIED** | Cryptographic token-based password reset via email; one-time magic link hash tokens. |
| **2.4.1** | Prevent brute-force attacks on credentials | **VERIFIED** | Supabase Auth rate limiting and client-side anti-hammering guards active. |
| **2.7.1** | Social authentication (OAuth) securely implemented | **FIXED** | Google OAuth availability probed before rendering button; prevents unsupported provider errors. |

## Chapter V3: Session Management
| Requirement | Description | Status | Architecture & Evidence |
|---|---|---|---|
| **3.1.1** | Session tokens are cryptographically strong | **VERIFIED** | High-entropy signed JWTs generated by Supabase Identity Provider. |
| **3.2.1** | Sessions terminate on logout | **VERIFIED** | `supabase.auth.signOut()` revokes session tokens and clears local storage. |
| **3.3.1** | Session tokens have reasonable expiration | **VERIFIED** | Access tokens expire in 1 hour with automatic refresh rotation via secure refresh tokens. |
| **3.4.1** | Inactive sessions terminate | **VERIFIED** | Inactive sessions time out; re-authentication required for privileged operations. |

## Chapter V4: Access Control
| Requirement | Description | Status | Architecture & Evidence |
|---|---|---|---|
| **4.1.1** | Principle of least privilege enforced | **VERIFIED** | Anonymous visitors have read-only access to approved public data; mutations denied by RLS. |
| **4.1.2** | Access control enforced server-side | **VERIFIED** | PostgreSQL Row Level Security (RLS) policies on all tables (`profiles`, `reports`, `campaigns`, `audit_logs`). |
| **4.2.1** | Prevent horizontal privilege escalation | **VERIFIED** | Citizens can only view/edit their own private reports; other citizens' reports blocked by RLS. |
| **4.2.2** | Prevent vertical privilege escalation | **VERIFIED** | Citizens cannot modify `role` in `profiles`. Role changes restricted to super_admin at AAL2. |
| **4.3.1** | Administrative PIN security | **VERIFIED** | Founder PIN validated server-side, requiring AAL2 multi-factor authorization. |
